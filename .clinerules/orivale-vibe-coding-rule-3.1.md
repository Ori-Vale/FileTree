# Ori Vale · Vibe Coding 规则

## 一、交互规范

- 克制、精准、严谨，摒弃 AI 机械感与废话。对话即 Code Review，直击本质。
- 严禁"作为AI"、"仅为示例"、"祝愉快"等套话。
- Debug 时拒讲基础概念，直击异常断点，直接给修复代码。
- 不怕问问题：任何不清楚的地方都可以问。

---

## 二、工作流

### 2.1 场景分级

默认 L2，用户可随时声明级别。涉及家族化模块时自动升级为 L1，AI 应主动提醒。

| 级别 | 场景 | 节奏 |
|---|---|---|
| **L1 严格** | 生产代码、家族化模块 | 最小单元，每步确认，全量规范 |
| **L2 标准** | 原型验证、学习探索 | 大步推进，关键节点确认，事后补齐注释与检查 |
| **L3 轻量** | 一次性脚本、临时实验 | 尽情推进，仅遵守交互规范与安全约束 |

### 2.2 执行原则

1. 动手前明确目标、梳理范围、Git 备份。
2. 最小任务单元开始，每步验证，不动正常旧逻辑。
3. 遇缺陷先提风险与方案，讨论后改。
4. 每次结束撰写总结报告（目标/成果/待办/经验）。

## 三、代码规范

### 3.1 硬编码、复用与命名

- 严禁写死数值/字符，优先引用已有资源。
- 新增前先查项目是否已有类似实现，避免重复。
- 功能相似时提取为公共函数或常量，常量集中管理。
- 涉及家族化设计时，使用品牌前缀 + 语义后缀（如 OriVale_xxx），调用风格保持一致。

### 3.2 注释

**原则：为理解服务，不为数量服务。**

必须注释：公开接口（文档注释）、非显而易见的业务逻辑、与直觉相反的写法、魔法值来源、非显而易见的依赖选型理由。
不必注释：代码本身已足够清晰的简单逻辑、标准用法。

格式要求：
- 中文，自然流畅，像给朋友讲解。
- 注释与代码同行，间距以可读性为准。
- 用分隔线和标题划分功能区块。
- 注释符号按语言选择（`//` `#` `<!-- -->` `/* */` `///` `"""` 等）。

### 3.3 质量与安全

- 遵循项目所用语言/框架的官方风格与最佳实践。
- 库、文件、常量、变量、函数、组件、样式、资源等所有命名均应有意义，避免单字母（循环变量除外）。
- 优先使用语言的安全机制处理错误，不使用危险操作，除非有明确理由并附注释。
- 新增依赖时说明用途，优先使用标准库/内置能力。

### 3.4 项目结构

项目结构清晰，相关功能归类存放，测试代码遵循框架约定位置。

## 四、家族化设计

**适用范围：** 所有以 OriVale 或 Senseline 开头或相关的库、文件、常量、变量、函数、组件、样式、资源。

涉及上述范围时，任何变更均需经用户知晓并同意。推荐方案并说明理由，提醒用户"这属于家族化设计内容"，最终决策由用户确认后执行。

---

## 五、协作规范

### 5.1 先读后改
修改已有文件前必须先读取当前内容，不得凭记忆修改。至少读取目标区域前后各 20 行。

### 5.2 变更范围控制
单次对话修改文件不超过 3 个，超过时先暂停列出计划，经确认后继续。跨文件重构按依赖顺序逐个修改、逐个验证。

### 5.3 上下文管理
长对话（超过 15 轮）后执行关键操作前重新读取相关文件。发现假设可能过时时主动确认。

### 5.4 错误处理
收到报错直接定位异常位置、给出修复代码。报错信息不完整时先请求完整信息，不要猜测性修复。修复后必须验证。

### 5.5 方案推荐
多种路径时列出不超过 3 个方案的核心取舍，给出推荐理由，由用户决定。

## 七、技术栈参考

> 按项目激活对应条目，其余保留。精确版本由项目配置文件决定，本章仅记录最低特性门槛。工具选择以项目现有配置为准，本节仅作新项目默认推荐。

### 7.1 Rust
最低 2021 edition（新关键字保留与闭包捕获行为）；精确版本见 `rust-toolchain.toml` / `Cargo.toml`
- **检查：** `cargo clippy`，不允许 warning
- **格式：** `cargo fmt`
- **错误处理：** 库用 `thiserror`，应用用 `anyhow`，优先 `Result`/`Option` + `?`
- **安全：** 禁 `unsafe`；禁 `.unwrap()`（除非附注释说明）
- **依赖：** `cargo add`，说明用途
- **测试：** `cargo test`，放 `tests/` 或模块内 `#[cfg(test)]`
- **文档：** `///` 公开接口，`//!` 模块级

### 7.2 Dart / Flutter
最低 Dart 3.0+（sound null safety、records、patterns）；精确版本见 `pubspec.yaml`
- **检查：** `dart analyze` / `flutter analyze`，遵循 `analysis_options.yaml`，不允许 warning
- **格式：** `dart format .`
- **错误处理：** `try-catch` + 自定义异常类，禁止空 `catch`
- **安全：** 避免 `dynamic` 滥用；避免 `!` 非空断言，优先 `?.` 和 `??`
- **依赖：** `flutter pub add` / `dart pub add`，说明用途
- **测试：** `flutter test`，单元测试放 `test/`，集成测试放 `integration_test/`
- **文档：** `///` 公开接口，覆盖参数说明与使用示例

### 7.3 Python
最低 3.10+（`match-case`、`X | Y` 类型联合）；精确版本见 `pyproject.toml`
- **检查：** `ruff check`，不允许 warning
- **格式：** `ruff format`
- **类型检查：** `mypy --strict`
- **错误处理：** 自定义异常继承体系，禁止裸 `except:`
- **安全：** 禁 `eval()`/`exec()`；禁 `type: ignore`（除非附注释）
- **依赖：** `uv add`（首选），说明用途
- **测试：** `pytest`，放 `tests/`，文件命名 `test_*.py`
- **文档：** Google 风格 docstring（`Args:` / `Returns:` / `Raises:`）

### 7.4 TypeScript / JavaScript
最低 TS 5.0+（`const` 类型参数、`satisfies`）；精确版本见 `package.json` / `tsconfig.json`
- **检查：** `eslint .`，启用 `@typescript-eslint/recommended`，不允许 warning
- **格式：** `prettier --write .`
- **错误处理：** 自定义 Error 子类，禁止 `any`，优先 `unknown` + 类型守卫
- **安全：** `strict: true`；禁止 `@ts-ignore`（除非附注释）
- **依赖：** `pnpm add`（首选），说明用途
- **测试：** `vitest`（首选），放 `__tests__/` 或 `*.test.ts` 同级
- **文档：** TSDoc，覆盖 `@param` / `@returns` / `@example`

### 7.5 Go
最低 1.21+（泛型稳定、`slog`、`min`/`max`）；精确版本见 `go.mod`
- **检查：** `golangci-lint run`，不允许 warning
- **格式：** `gofmt -s -w .`
- **错误处理：** `fmt.Errorf("上下文: %w", err)` 包装，禁止 `panic`（初始化等不可恢复场景除外）
- **安全：** 禁 `unsafe`；禁止忽略错误（`_ = err` 需显式标注并注释）
- **依赖：** `go get`，说明用途，定期 `go mod tidy`
- **测试：** `go test ./...`，同目录 `*_test.go`
- **文档：** Godoc 注释，首行以函数名开头
